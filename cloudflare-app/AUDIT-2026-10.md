## 1. Where things stand

- **Live app:** `compass.sagemodeai.com`, Cloudflare Pages, built from `main`,
  root directory `cloudflare-app/`. Deploy = push to `main`.
- **Feature branch** `claude/astrology-chart-analysis-obkvN` is kept level with
  `main` by merging (never force-push). Edit on the branch, then mirror
  `cloudflare-app/` and `.claude/` to `main`.
- **`vercel-app/` is an older copy the owner still uses. Do not touch it.**
- **Architecture:** everything astrological (natal, houses, aspects, Human
  Design, Gene Keys, numerology, the Timeline and its day readings) is computed
  in the browser and costs nothing. Only three things call the model:
  conversation turns, the two portrait documents (Story / Analysis), and the
  Book-memory digest. All data lives in the user's browser (localStorage).
- **Model routing** by tier: `chat` → `MODEL_CHAT`, `deep` → `MODEL_DEEP`
  (portraits and Together), `summary` → `MODEL_SUMMARY` (digest). Unset tiers
  fall back to `claude-sonnet-4-6`.
- **Prompt caching** (added Sept): the chart + portrait + rules sit in a cached
  system block; the changing part (date, sky, journal, mode) is frozen per
  session so follow-ups read the prefix from cache.
- **Access:** per-person codes in `ACCESS_CODES` (`label:code` entries), or a
  user's own key (BYOK). Optional usage tally in a KV namespace `USAGE`, with a
  report at `/api/usage?key=ADMIN_KEY`.
- **Added in September by a separate session:** Timeline tab (day-by-day
  transits), day readings, Focus layer with 8 modes incl. Play, "Ask about this
  day", Together overlay on the Timeline, prompt caching.

## 2. Findings, ranked

### P0 — bugs that break or mislead

1. **Sessions die after 12 exchanges.** `send()` pushes the user message, then
   sends `S.messages.slice(-24)` (app.js:310, 364). At the 13th message the
   slice starts with an assistant turn, the API rejects it, the "safety net"
   retries on the default model and fails identically. Fix: trim in blocks that
   always start at a user message (when > 24, drop the oldest 8), which also
   keeps the cached prefix stable for several turns.
2. **Portraits do not stream.** `generateDoc(prompt, onChunk)` is never given
   `onChunk` (engine.js:274, 277; app.js:680). The overlay waits in silence for a
   long generation. Pass the renderer's chunk handler through.
3. **Backup exports the access code** (app.js:454-516) while the privacy note
   says keys are excluded. Strip `cc_access` from export.
4. **Book memory goes stale and is invisible.** `clearSessions` and
   `deleteProfile` leave `cc_<id>_memory`; with zero sessions the digest is
   never rebuilt but is still injected into every prompt. There is no UI to see
   or reset it. Fix: delete it on clear/delete; show it under Book with a
   "Forget" button.
5. **No way to delete a profile.** `deleteProfile` (core.js:114) has no caller.
6. **Retry on any upstream failure** (chat.js:162) doubles pressure on 429/529.
   Retry only on a model-not-found class of error.

**Per-turn baseline today** (Sonnet-class chat): warm turn ≈ $0.01, cold turn
(new session, mode change, >5-min pause) ≈ $0.04. Portrait pair ≈ $0.25 once

messages a month costs roughly **$1-2/month**; ten testers ≈ **$10-20/month**.
Before the fixes, 2-3× that, mostly from the digest. Verify current prices and
model IDs at docs.claude.com before relying on these.

### Mobile — why typing is unreliable on the iPhone PWA

Root causes, all confirmed in code:

- **Input font is 14px** (styles.css:527). iOS zooms the page on focus for any
  field under 16px; zoom shrinks `visualViewport.height`, `--app-h` follows,
  and the zoom persists after blur. Whether it fires depends on how focus
  happened — that is the "sometimes visible, sometimes not". Same on wizard
  inputs, journal textarea, timeline date/select.
- **`visualViewport.offsetTop` is ignored** (app.js:755-770). With
  `html,body{overflow:hidden}` iOS offsets the visual viewport to reveal the
  field; the fixed `.app` stays anchored to the layout viewport, so the header
  slides off and the composer lands offscreen.
- Focus handling is two blind timers (350 ms / 300 ms) that race the keyboard
  animation.
- No `enterkeyhint`; Enter sends and iOS has no Shift, so no newline is possible.

Minimal fix list, in order (all scoped to the ≤680px media query unless noted):

1. `font-size: 16px` on every text input/select/textarea in the media query;
   remove the three inline `font-size:0.78rem` in engine.js:103,107,111.
   Never use `maximum-scale=1`.
2. `setAppHeight` also sets `--app-top = visualViewport.offsetTop`; `.app`
   gets `top: var(--app-top, 0)`; re-scroll `.convo` on the next frame when the
   input has focus. Keep the timers as fallback.
3. `enterkeyhint="send" autocapitalize="sentences"` on the textarea.
4. `overscroll-behavior: none` on html/body, `contain` on every scroller.
5. Sidebar scrim (`.sb-scrim`) with outside-tap close.
6. Tap targets ≥ 40px: `.btn-sm .starter .chip .pt-tab .sb-row button
   .btn-icon`; Timeline bars `min-width: 8px`, strips `overflow-x: auto`.
7. Tabs as a 5-column grid so "Portrait" is not off-screen.
8. Portrait reading padding 16px; transcript text 0.85rem.
9. Muted-text contrast: dark `#8f8fb3`, light `#6f5e46` (affects desktop, on purpose).

Cannot be verified headless: iOS keyboard behaviour, focus zoom, `offsetTop`
during animation, safe-area gap while the keyboard is up. **The owner tests
on-device**: focus by tap, by starter chip, and after rotation; then a 13+
message conversation.

## 3. Sharing with a small test group — "my wallet, not theirs"

Principle: testers use **your key through their access code**, with a
**per-code monthly budget** enforced by the proxy. BYOK stays available but is
never required. A spend cap on the key at console.anthropic.com remains the
hard backstop.

Build (chat.js):

1. **Pre-check before the model call.** Read `usage:${label}`; if the month's
   count (or token tally) ≥ cap → `429 {error, code:'budget', used, limit,
   resetsOn}`. Skip for BYOK. KV is eventually consistent, so this is a soft cap
   — fine for friends.
2. **Count real tokens, not calls.** The stream loop already parses every SSE
   event; keep `message_start.usage` and `message_delta.usage.output_tokens`,
   weight by a per-model price map, write at stream end.
3. **Per-tier caps:** e.g. ≤ 4 portrait generations/month per code, so a
   regenerate loop cannot burn the budget.
4. Client: `llmComplete` surfaces `code:'budget'`; `send()` shows used/limit/
   reset date and offers BYOK; `maybeUpdateMemory` stops retrying; optionally
   `validateOnly` returns remaining budget for a small sidebar meter.

Suggested caps for a first round: **150 messages or ~$3/month per code, 4
portrait generations**. Revisit after one month of `/api/usage` data.

Model settings: see the table in §10 (decided).

## 5. Feedback from testers

Today there is **no** way to send feedback inside the app. "Is there a chat?"
— the app's chat is with the model; a live chat with you is not worth building
for a small group. Build instead:

- Sidebar row **Feedback** → small overlay (textarea, not `prompt()`), with the
  current tab and app version attached automatically.
- POST `/api/feedback` → `USAGE.put('feedback:<ts>', {label, text, tab, lang,
  version})`. The access-code label comes from the existing `codes(env)`.
- `/api/usage` lists feedback under the usage table, newest first.
- Pair it with a group chat (WhatsApp/Signal) for conversation; the in-app box
  is for the moment something feels off.

## 10. Decisions (owner, 2026-10-06)

1. **Testers:** up to 5. Learn first, cap later → Phase 2 ships the tally and
   the budget mechanism with **generous caps** (e.g. $10/code/month, 6
   portraits) so nobody is blocked in month one; tighten from `/api/usage`
   data after that. The key's spend cap at console.anthropic.com is the real
   ceiling meanwhile.
2. **Calendar:** export only (Option A). **No sensitive data on the server** —
   Options B and C are off the table for now. Phase 6 removed.
3. **Model variables:** not set, so everything runs on `claude-sonnet-4-6`.
   Set these in Cloudflare → Settings → Variables, then retry the deployment:

   | Variable | Value | Why |
   |---|---|---|
   | `MODEL_CHAT` | `claude-sonnet-5-5` | current Sonnet; **cheaper than the 4.6 default** ($2/$10 vs $3/$15 per MTok) |
   | `MODEL_DEEP` | `claude-sonnet-5-5` | Together conversation; portraits move to `MODEL_DOC` in Phase 2 |
   | `MODEL_SUMMARY` | `claude-haiku-4-5` | memory digest ($1/$5) |
   | `MODEL_DOC` (Phase 2) | `claude-opus-5-5` | portraits only ($4/$20, cache reads $0.20) |

   Two consequences for the proxy, both in Phase 1: the 5.5 models run
   **adaptive thinking by default**, which adds billed output tokens to every
   chat reply — set `output_config: {effort: 'low'}` for the `chat` tier and
   `medium`/`high` for documents. And they can return `stop_reason:
   "refusal"`; the stream parser only forwards text deltas, so handle that
   with a visible message instead of silence.
4. **"Adaptive model choice by question":** not a lot to ask, but a content
   classifier would be an extra model call per message for little gain. The
   modes already *are* the routing signal (Reflect vs Question vs Transits vs
   Together), and the tiers are wired to them. The cheap, real version of
   "adaptive" is **effort per tier on one model** — low for everyday chat,
   higher for portraits — which keeps a single cache namespace. Revisit
   content-based routing only if usage data shows a need.
5. **Feedback:** in-app box (§5) plus a WhatsApp/Signal group. The shared
   chat link was a misunderstanding — nothing to import.

## 11. Re-audit (2026-10-06, after Phase 1) — what held, what did not

A second session re-read every file against every claim in §2-§7. Full table with
line references: `AUDIT-2026-10-reaudit.md` (same folder). The short version:

**Overstated.** P0 #1 ("every conversation dies at the 13th message"). The arithmetic
was right (a 24-message slice opens on a reply at the 13th send), but the owner has
had longer conversations without an error, so the API no longer rejects a history
that opens with a reply; and the "retries on the default model" half was wrong (the
old proxy only retried when a `MODEL_*` variable was set, which it was not). The
block-trim change stays for a different reason: a sliding window changed the start
of the history on every message after 24, which threw away the cached prefix each
turn. P0 #6 was overstated the same way (the retry never fired in production).

**Confirmed.** P0 #2-5; cost 1-4 and 6 (all done in Phase 1); every mobile root
cause that is checkable in code (14px inputs, no `offsetTop`, blind timers, no
`enterkeyhint`; muted-text contrast measured 3.4-4.3:1, fails AA); the dead-code
and feature gaps. None of the nine mobile fixes is implemented yet (Phase 3).

**Cannot verify headless.** Whether the API accepts an assistant-first history; iOS
keyboard behaviour; a real 5.5 refusal; whether `max_tokens` 2000 at effort `low`
ever truncates a chat reply (M7 — watch for the "length limit" note).

**Missed by the October audit, now fixed (v19):** M1 proxy took `model` and
`max_tokens` from any code holder (pinned to the tier now; BYOK keeps the freedom);
M3b service worker cached the `/api/usage?key=…` page; M4 unescaped profile names in
the Timeline synastry header; Phase 1 diff nits B1-B7 (digest ids vs sent batch, notes
replayed to the model, over-broad model-rejection match, Forget lagging behind the
cached block, memory chapter hidden with zero sessions, wizard counter).

**Missed, still open, scheduled:** M2 racy KV tally → Phase 2 (rewritten as a
token tally); M3a `ADMIN_KEY` in the query string with a plain compare → Phase 2;
M5 the English sidebar rows are eight missing i18n keys per language, and the new
Profile → Delete row needs them too → Phase 5; M6 journal entries written
mid-session reach the model only in the next session (deliberate, for caching —
document it in the privacy/help text) → Phase 5; M8 OpenAI branch sends
`max_tokens` where newer models want `max_completion_tokens`, BYOK only → Phase 5
(or document as unsupported); M9 no CSP/frame/referrer headers → Phase 5.

**Lesson for the next audit:** a claim derived from code plus a documented API rule
is a hypothesis until a request has been seen to fail. Mark such claims
"unverified" in the findings, and test them against the live app before calling
them P0.
